# 데이터셋 카탈로그 (weather_fit)

데이터셋 정의서. 각 소스의 **엔드포인트 / 인증 / 백필 가능 여부 / 한도 / 저장 경로**를 확정한다.

- 대상 지역: **서울** (ASOS 지점 `108`, 예보관서 `109`, 중기육상 `11B00000`, 중기기온 `11B10101`)
- 대상 기간: 수집 **2018-01-01 ~ 현재**, 기본 분석 구간 **2023-01-01 ~** (2020~2022 코로나 구간은 민감도 분석용. `docs/prd.md` §5)
- 저장 포맷: CSV, 월 파티션 `{yyyy-mm}.csv`

## 1. 기상 데이터 (기상청 API 허브)

전부 `authKey` 하나로 조회한다. 공공데이터포털(data.go.kr)과 **인증체계가 완전히 별개**이므로 키를 혼용하지 말 것.

베이스: `https://apihub.kma.go.kr/api/typ01/url/`

### W1. 지상관측 일자료 (ASOS) — 분석의 기준선

```
GET kma_sfcdd3.php?tm1=20230101&tm2=20230131&stn=108&disp=1&help=0&authKey={KEY}
```

- **기간 조회 최대 31일** → 3년 백필 = 월 단위 43회 호출
- ⚠️ **`kma_sfcdd3.php` 는 `disp` 를 무시하고 항상 공백 구분으로 응답한다.** 반면 중기예보(`fct_afs_*`)는 `disp=1` 에서 쉼표 구분 + 행 끝 `=` 마커다. **파라미터를 믿지 말고 응답에 쉼표가 있는지로 분기**할 것
- ⚠️ **결측 표기 `-9.0` / `-99.0` 을 일괄 치환하면 실제 관측값이 파괴된다.** 서울 1월 `TA_MIN=-9.0` 은 진짜 -9.0℃다. 컬럼의 물리적 정의역으로 분기해야 한다 — 기온류(`TA_`/`TD_`/`TS_`/`TG_`)는 `-99` 계열만 결측, 음수가 불가능한 컬럼(강수·습도·풍속·적설)은 `-9` 계열도 결측
- ⚠️ **`RN_DAY = -9.0` 은 결측이 아니라 무강수다** (1,308일 중 754일, 57.6%). `processed` 단계에서 `0.0` 으로 채운다. raw에서 채우면 진짜 결측과 영영 구분할 수 없어 그대로 둔다
- 주요 항목: `TA_AVG`(평균기온) `TA_MAX` `TA_MIN` `RN_DAY`(일강수) `HM_AVG`(습도) `WS_AVG`(풍속) `CA_TOT`(운량)
- 이 데이터가 `weather_daily` 의 실체다. **일교차·Δt·체감온도는 여기서 파생**시킨다.

> 예보(W2·W3)가 아니라 **관측(W1)이 EDA와 이벤트 정의의 기준**이다. 예보는 모델 입력일 뿐이다.

### W2·W3. 중기예보 발표분 아카이브 — "그날 알 수 있었던 정보"

```
GET fct_afs_wc.php?tmfc1=2023010106&tmfc2=2023013118&reg=11B10101&disp=1&authKey={KEY}   # 기온
GET fct_afs_wl.php?tmfc1=...&tmfc2=...&reg=11B00000&disp=1&authKey={KEY}                 # 육상(하늘/강수확률)
```

- 발표시각(`tmfc`) 기준 과거 조회 가능, **보유 2012-12-18 18:00 KST ~ 현재**
- 중기예보는 **1일 2회(06/18 KST) 발표**, 3~10일 후를 예보
- 응답: `MIN`/`MAX`(기온), `SKY`, `PRE`, `RN_ST`(강수확률), `WF`
- 서울 기온구역 `11B10101`, 육상구역 `11B00000`(서울·인천·경기)

> **이 데이터셋이 이 프로젝트의 차별점이다.** 관측치로 학습한 모델은 "내일 실제 기온"을 아는 셈이라 실전에서 못 쓴다. 발표분 아카이브를 쓰면 **예보 오차까지 포함한 현실적인 모델**이 된다.
>
> ✅ 과거 발표분 조회 **가능 확인** (2023-01-01~2026-07-31 구간을 실제로 받아 2,616 발표분 = 1,308일 × 2회 확인. 기상 데이터는 저장소에 담지 않으므로 수집기로 다시 받는다).
>
> ⚠️ **조인 규칙 정정**: 중기예보의 최소 리드타임은 **3일**이다(실측 2.2~9.8일). 따라서 "발표일 D-1 → 대상일 D" 조인은 **성립하지 않는다 — 그런 행이 아예 없다.** 올바른 규칙은 대상일 D에 대해 `tmfc < D` 인 발표분 중 **가장 최신**을 고르는 것이고, 실제로는 D-3 발표가 선택된다. 이것이 "그날 실제로 알 수 있었던 예보"다.
>
> ⚠️ `MOD=A02`(12시간)는 같은 대상일에 00시·12시 두 행을 만든다. 일 단위로 접는 규칙(최고/최저/평균 중 무엇)을 transform에서 정해야 한다.
>
> ⚠️ `fct_afs_wc.php` 는 **기상청 문서 자체에 번호 오타**가 있다 — `MAX`/`MIN_L`/`MIN_H`/`MAX_L`/`MAX_H` 가 전부 "11."로 매겨져 있어, 번호 목록을 믿으면 5개 컬럼이 사라진다. `fct_afs_wl.php` 도 문서 14개 vs 실제 출력 11개다(`MAN_ID`/`MAN_FC`/`REG_NAME` 미출력). **헤더 주석의 마지막 컬럼명 라인을 파싱**해야 한다.

### W4. 기상특보 발표 이력 — 이벤트 라벨의 정답지

```
GET wrn_reg.php?authKey={KEY}                                       # 특보구역 코드 조회 (서울 구역코드 확인용)
GET wrn_met_data.php?tmfc1=20230101&tmfc2=20231231&reg={서울}&authKey={KEY}
```

- **보유 2004-06-30 ~ 현재**. `reg` 파라미터는 **서버측 필터로 정상 동작**한다(전국 2,318행 → 권역 8행)
- 실제 컬럼 순서: `TM_FC, TM_EF, TM_IN, STN, REG_ID, WRN, LVL, CMD, GRD, CNT, RPT, T01~T18` — **문서 순서와 다르다**
- 특보종류(`WRN`): `C`한파 `H`폭염 `R`호우 `S`대설 `D`건조 `W`강풍
- 등급(`LVL`): `1`주의 `2`주의보 `3`경보
- 명령(`CMD`): `1`발표 `3`해제 `6`변경

> **문서 오류 3건 — 실측으로 확정한 것들**
>
> 1. `wrn_table.html` 의 `C=대설, D=한파` 는 **틀렸다.** 3년 실측 분포로 확정: `C`=한파(143건, 겨울 84.6%·여름 0%), `H`=폭염(216건, 여름 84.3%), `S`=대설(겨울 81.5%), `D`=건조.
> 2. **`TM_ED`(해제시각) 컬럼은 없다.** 해제는 `CMD=3` 인 **별도 행**이다(발표 710 / 해제 536 / 변경 132). 발효구간은 발표–해제 행을 짝지어 transform에서 조립해야 한다.
> 3. **서울 광역코드 `L1100000` 은 4년간 0행이다.** 특보는 2020-05-14부터 4개 권역(`L1100100`동남 `L1100200`동북 `L1100300`서남 `L1100400`서북)으로만 발표된다. 또 `wrn_reg.php` 에 '서울'이란 이름이 둘 있고 앞엣것(`L1010100`)은 2020년 만료분이라, **이름으로 집으면 역시 0행**이 된다. 유효기간 필터 + 하위권역 자동 포함으로 해결한다.
>
> → 서울 전체에 특보가 있었는가를 정의하려면 4개 권역을 어떻게 집계할지(any / 과반 / 권역별 유지) 결정해야 한다. 분석 설계 이슈다.
>
> **활용 포인트**: PRD의 룰 기반 이벤트 정의(한파 `t_min ≤ -12℃` 2일 지속 등)를 실제 특보 발표와 대조하면 "우리 룰이 얼마나 맞는가"를 정량 검증할 수 있다. 원안에 없던 분석이고, 리포트에서 가장 설득력 있는 장면이 된다.

### T1. 쇼핑인사이트 — 카테고리별 클릭지수 ★ 메인 타깃

```
POST https://naverapihub.apigw.ntruss.com/shopping/v1/categories
Headers: X-NCP-APIGW-API-KEY-ID, X-NCP-APIGW-API-KEY, Content-Type: application/json
Body: {
  "startDate": "2023-01-01", "endDate": "2026-07-31", "timeUnit": "date",
  "category": [ {"name": "여성의류", "param": ["50000167"]}, ... ]   // 최대 3개
}
```

- **요청당 카테고리 최대 3개**, `timeUnit`: `date` | `week` | `month`
- 데이터 보유 2017-08~ → 3년 백필 문제없음
- 선택 필터: `device`(pc/mo), `gender`, `ages`
- **지역 파라미터 없음** (공식 문서로 미지원 확인). 지역 분해가 필요하면 `T7` 구글 트렌드로 보완한다.

#### ⚠️ 상대지수 정규화 — 이 데이터셋 최대의 함정

응답 `ratio`는 **"요청에 포함된 카테고리들 × 요청 기간" 안에서의 최댓값을 100으로 한 상대값**이다. 요청 묶음이 다르면 **스케일이 달라 서로 비교할 수 없다.**

두 가지 규칙으로 방어한다.

1. **기간을 쪼개지 말 것.** 3년 전체를 `timeUnit=date` 한 번에 요청한다. 부득이 분할하면 30일 이상 겹치는 구간을 두고 겹침 구간 비율로 체이닝(chaining)한다.
2. **앵커 카테고리를 넣을 것.** 3개 슬롯 중 1개를 모든 요청에 공통으로 넣는 기준 카테고리(예: `패션의류` 대분류)로 고정하고, 나머지 2개만 교체한다. 수집 후 앵커 대비 비율로 재스케일링하면 전체 카테고리를 하나의 축에 올릴 수 있다.

```
요청1: [앵커, 여성의류, 남성의류]
요청2: [앵커, 가방,   신발]
→ 저장 시 rescaled = ratio / anchor_ratio  (같은 날짜 기준)
```

이 처리를 하지 않으면 **카테고리 간 비교가 전부 무효**가 된다. 반드시 원본 `ratio`와 `rescaled`를 둘 다 저장한다.

> ⚠️ **날짜별 `rescaled`는 같은 날 품목끼리 비교할 때만 쓴다. 시계열 분석·모델 목표로 쓰지 않는다.** 분모인 앵커도 계절을 탄다(T3·T4 앵커 `반팔티`의 월 중앙값이 1월 1.4 → 5월 9.3). 날짜별로 나누면 앵커의 계절성이 모든 품목에 거꾸로 섞인다. 시계열에는 배치마다 상수 하나로 스케일만 맞춘 `level`을 쓴다. 정의는 `docs/prd.md` §8.2.

#### 카테고리 cid

대분류는 확정값, 중분류는 수집 시 확인이 필요하다.

| 대분류 | cid |
|---|---|
| 패션의류 | `50000000` |
| 패션잡화 | `50000001` |
| 화장품/미용 | `50000002` |
| 스포츠/레저 | `50000007` |

중분류 cid는 카테고리 조회 API가 없다. `https://search.shopping.naver.com` 카테고리 페이지 URL 또는 데이터랩 웹 UI의 네트워크 요청 페이로드에서 추출해 `configs/categories.yaml` 에 기록한다. **출처 URL을 주석으로 남길 것.**

### T2. 카테고리 × 성별·연령·기기

```
POST /shopping/v1/category/device
POST /shopping/v1/category/gender
POST /shopping/v1/category/age
```

T1과 달리 **`category` 가 배열이 아니라 cid 문자열 하나**다(요청당 카테고리 1개). 응답 `data[]` 에 `group`(pc·mo / m·f / 10~60) 필드가 붙는다. 수집기는 아직 없다 — 필요하면 T1 수집기를 본떠 추가한다. "한파 때 반응하는 연령대가 다른가" 같은 질문에 쓴다. 없어도 본류 분석은 가능하므로 P1.

### T3. 쇼핑인사이트 — 키워드별 클릭지수 ★ 세분 타깃

```
POST /shopping/v1/category/keywords
Body: { "startDate":..., "endDate":..., "timeUnit":"date",
        "category": "50000167",
        "keyword": [ {"name":"패딩","param":["패딩"]}, ... ] }   // 최대 5개, param 은 1개만
```

- **요청당 키워드 최대 5개** → 날씨민감 30개 = 6회 요청 (앵커 포함 시 8회)
- 중분류("여성의류")는 너무 뭉뚱그려져 날씨 효과가 희석된다. **패딩·트렌치코트·우산 같은 실제 신호는 이 데이터셋에 있다.**
- T1과 동일한 정규화 함정이 그대로 적용된다. 앵커 키워드 1개 고정 필수.

### T4. 검색어트렌드 (쇼핑 밖 검색 수요)

```
POST https://naverapihub.apigw.ntruss.com/search-trend/v1/search
Body: { "startDate":..., "endDate":..., "timeUnit":"date",
        "keywordGroups":[ {"groupName":"패딩","keywords":["패딩","롱패딩"]} ] }  // 그룹 최대 5, 그룹당 키워드 20(FAQ는 5 — 5 이하로 설계)
```

- 2016-01-01~ 조회 가능
- 쇼핑 클릭(T1/T3)은 **구매 직전** 신호, 검색어트렌드는 **관심 단계** 신호다. 둘의 시차가 PRD H3의 검증 재료다.

### ~~T5. 카테고리 인기검색어 TOP500~~ — 범위 제외

데이터랩 웹의 "인기검색어" 순위는 공식 API에 없고 웹 UI 내부 엔드포인트로만 얻을 수 있다. 언제든 막힐 수 있고 ToS 회색지대라 범위에서 뺐다. 순위형 신호가 필요하면 T3 `level`로 일별 순위를 직접 매긴다.

### ~~T6. 네이버 쇼핑 검색 API~~ — 폐기

`/v1/search/shop.json` 은 **2026-07-31자로 종료**됐고 NAVER API HUB에도 대체 API가 없다(제3자 정리 글 기준, 네이버 공지 원문 미확인). 책·전문자료 검색도 함께 종료됐다.

상위 노출 상품 스냅샷은 이 프로젝트에서 포기한다. 순위형 신호가 필요하면 **`T3` 키워드 클릭지수의 일별 순위를 직접 매긴다.** 공식 데이터로 재현할 수 있어 오히려 방어하기 쉽다.

### T7. 구글 트렌드 — 유일한 서울 지역 분해 소스

```python
pytrends.build_payload(["패딩"], timeframe="2023-01-01 2026-07-31", geo="KR-11")  # KR-11 = 서울
```

- 토큰 불필요, **비공식 라이브러리** (429 잦음 → 요청 간격 필수)
- 네이버 데이터랩에 지역 필터가 없으므로, "서울 한정 분석"이라는 PRD 전제를 데이터로 뒷받침할 수 있는 **유일한 소스**다
- 전국(`KR`) 대비 서울(`KR-11`) 지수 차이를 보면 "서울에 국한한 분석이 타당한가"를 검증할 수 있다
- 역시 0~100 상대지수 — 요청 단위 정규화 함정 동일

### 씨드 수집에서 실측된 데이터 특성 (2026-07 · 2026-08-18 수집)

문서상 스펙이 아니라 **실제 응답에서 확인된 것**들이다. 3년 백필 때 훨씬 크게 드러난다.

**① T3는 클릭이 적은 날의 행을 통째로 누락시킨다 — `ratio=0`이 아니라 행 자체가 없다.**

2026-07 기준 롱패딩 28/31일, 레인코트 1/31일, **방수자켓은 0건이라 파일에 아예 존재하지 않는다.** 그대로 join하면 조용히 NaN이 되어 평균·상관이 왜곡된다. `processed` 단계에서 날짜축을 reindex한 뒤 **"결측 = 0인가, 미관측인가"를 명시적으로 결정**해야 한다.

겨울 키워드를 여름에 뽑으면 이 현상이 심해지므로, 3년 백필에서는 계절 반대 구간이 통째로 비는 시리즈가 생긴다. 이 결정은 분석 결과를 바꾸므로 노트북에 근거를 남길 것.

반대로 **T4(검색어트렌드)는 희소 키워드도 31/31일을 채워 반환한다.** 두 소스의 결측 규약이 다르다.

**② 앵커 재정규화의 필요성은 T3·T4에서 실증됐다.**

T3·T4는 앵커('반팔티')의 raw `ratio`가 배치마다 실제로 달랐다 → 재정규화 없이는 비교 불가.
T1은 배치 간 raw `ratio`가 우연히 일치했는데, 이는 API 성질이 아니라 **앵커('패션의류')가 항상 최대 카테고리라 분모가 같았을 뿐**이다. 앵커보다 큰 카테고리가 배치에 들어오면 스케일이 바뀐다 — "T1은 raw를 그냥 써도 된다"고 일반화하면 안 된다.

**③ T3의 `rescaled`는 카테고리를 가로질러 비교할 수 없다.**

T3는 "카테고리 안에서의" 상대값이라 cid가 다르면 앵커도 다르다(패션의류=반팔티 vs 패션잡화=양말). **카테고리를 넘는 비교는 T4를 써야 한다.**

**④ 네이버 실제 카테고리 트리는 원안과 다르다.**

가방·신발은 단일 중분류가 없고 성별로 갈린다(4개로 분리). 우산은 중분류가 아니라 소분류(`50001482`)다 — API가 소분류 cid도 받으므로 그대로 수집한다. **"액세서리"는 정확한 대응이 없어 주얼리(`50000189`)로 택했다 — 재검토 여지 있음** (후보: 패션소품 `50000185`, 헤어액세서리 `50000184`).

### NAVER API HUB 발급 절차

1. [네이버클라우드 콘솔](https://console.ncloud.com) 가입 후 리전 `한국`, 플랫폼 `VPC` 선택
2. Services > Application Services > **NAVER API HUB** > **서비스 이용 신청**(약관 동의)
3. **Application 등록** → API 목록에서 **쇼핑인사이트**와 **검색어 트렌드**를 둘 다 체크. 둘은 별개 API라 하나만 넣으면 다른 쪽이 실패한다
4. Application 관리 > 대상 선택 > API 관리의 **인증 정보** → Client ID / Client Secret 을 `.env` 의 `NAVER_API_HUB_CLIENT_ID` / `NAVER_API_HUB_CLIENT_SECRET` 에 넣는다
5. 계정 단위 IAM 키(`ncp_iam_…`)는 HUB 인증에 쓰지 않는다. 401이 나면 이 키를 넣지 않았는지 먼저 본다
6. 사용량은 콘솔에서 본다. 월 한도의 50·80·100%에서 메일 알림이 온다

weather_daily (                 -- W1 지상관측
  date DATE, region STRING,
