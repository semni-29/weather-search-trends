## 1. 요약

서울의 기상(관측·예보·특보)과 네이버 데이터랩의 패션 수요 지수를 결합해 세 가지를 만든다.

1. **분석 리포트** — 기온 급변·한파·폭염·호우 같은 날씨 충격이 어떤 품목 수요를 며칠 동안 얼마나 움직이는지 계절성을 걷어낸 뒤 추정한다.
2. **예측 모델** — 그 시점에 실제로 공개돼 있던 예보만으로 며칠 뒤의 품목별 수요 상승(lift)을 예측하고, 상승이 클 품목 Top-K를 고른다.
3. **웹 서비스** — 예측과 분석 결과를 탐색할 수 있는 대시보드. 정적 산출물과 API 계약을 두고 프론트엔드를 따로 구현한다.

세 산출물 모두 `make` 한 번으로 원천 수집부터 재현할 수 있어야 한다.

## 2. 배경과 문제

계절 단위 상품 기획은 "11월이면 패딩"처럼 달력을 따른다. 실제 수요는 달력보다 날씨에 먼저 반응한다. 첫 영하, 열흘 만의 10℃ 일교차, 장마 시작처럼 **평년에서 벗어나는 순간**에 특정 품목 검색과 클릭이 몰린다. 이 반응의 크기와 지연을 정량화하면 노출·재고·마케팅 시점을 며칠 앞당길 수 있다.

설계 단계에서 다음 문제를 확인했고, 이 문서는 그에 맞춰 범위와 기준을 정한다.

| 확인한 문제 | 처리 |
|---|---|
| "내일 예보 → 추천"이 직관적이지만, 과거 발표분을 받을 수 있는 중기예보는 최소 리드타임이 3~4일이라 D+1 예보 아카이브가 없다 | 기본 예측 대상을 **중기예보 최소 리드타임 시점(현재 D+4)**으로 둔다. D+1은 단기예보 아카이브를 확보할 때만 확장 범위로 둔다 (§8.1) |
| 목표 변수가 원 지수(0~100)라 카테고리 순위가 계절에 따라 거의 고정된다. Top-3 정확도가 높아도 의미가 없다 | 목표를 **계절성 제거 후 lift**로 정의하고, 계절 나이브 베이스라인 대비 개선으로 평가한다 (§8.2) |
| 모델 학습에 관측 기온을 쓰면 실전에서 알 수 없는 정보를 쓰게 된다 | 피처는 예측 시점에 공개된 데이터만 허용한다. 누수 규칙과 검사 코드를 둔다 (§8.4) |
| 분석이 노트북에만 있으면 재현이 안 된다 | 수집 → 정제 → 피처 → 모델 → 산출물을 모듈과 CLI로 만들고 CI에서 테스트한다 (§10) |
| 네이버 데이터랩이 NAVER API HUB로 이관됐고 쇼핑 검색 API는 종료됐다 | 수집기를 HUB 기준으로 전환했다. 종료된 소스는 범위에서 뺀다 (§5) |

## 3. 목표와 비목표

### 목표

- **G1. 인과에 가까운 효과 추정** — 날씨 충격 이후 품목별 수요 반응을 시차별로 추정하고 불확실성 구간을 함께 낸다.
- **G2. 실전 조건의 예측** — 예측 시점에 공개된 예보만 써서 D+4 lift를 예측하고, 계절 나이브보다 유의미하게 낫다는 것을 백테스트로 보인다.
- **G3. 쓸 수 있는 서비스** — 비전공자도 "다음 주 무엇이 뜨는가"와 "왜 그렇게 보는가"를 화면에서 이해할 수 있게 만든다.
- **G4. 재현 가능한 엔지니어링** — 누가 클론해도 같은 결과가 나오는 파이프라인, 테스트, CI, 문서.

### 비목표

- 실제 판매량·매출 예측. 데이터랩 지수는 상대값이라 절대 수요를 말할 수 없다. 월 단위 거래액(KOSIS)으로 방향만 검증한다.
- 지역별 분석. 데이터랩에 지역 필터가 없다. 서울 날씨 × 전국 수요 구조임을 리포트 첫 장에 명시한다.
- 개인화 추천. 사용자 데이터가 없다.
- 비공식 크롤링에 의존하는 기능. 인스타그램·무신사·쇼핑 검색 순위는 범위에서 뺀다.
- 상시 운영 서비스. 일 배치를 돌릴 수 있게 만들되 24시간 운영을 약속하지 않는다.

## 4. 연구 질문과 가설

모든 가설은 **검증 방법과 판정 기준을 미리 적고** 분석한다. 결과를 본 뒤 기준을 바꾸면 그 사실을 리포트에 남긴다.

`notebooks/01_eda.ipynb`에 2023-01 ~ 2026-07 데이터로 한 탐색 결과가 있다. 예비 결과일 뿐이므로 확정하지 않고, 아래 가설의 출발점으로 쓴다. 특히 노트북 §7은 "ΔT는 어떤 키워드도 설명하지 못하고, 설명력은 평년 대비 기온 편차에 있다"고 봤다. H1은 이 결과를 더 긴 기간과 교차검증으로 다시 확인한다.

| ID | 질문 | 가설 | 검증 방법 | 판정 기준 |
|---|---|---|---|---|
| H1 | 수요를 가장 잘 설명하는 기온 표현은 무엇인가 | **평년 대비 기온 편차**가 절대 기온·ΔT(전일 대비)·일교차보다 lift 설명력이 크다 (EDA 예비 결과) | 계절성 제거 lift에 대해 표현별 모형의 시계열 교차검증 오차 비교. ΔT는 일 단위와 3일 누적, 급강하 이벤트 단위로도 본다 | 편차 모형의 오차가 품목 과반에서 가장 작고, 차이의 부트스트랩 95% 구간이 0을 넘지 않음 |
| H2 | 특보는 같은 기온 수준을 넘어선 추가 반응을 만드는가 | 한파·폭염·호우 특보 발효일에는 기온만으로 설명되지 않는 lift가 있다 | 이벤트 스터디. 기온을 통제한 회귀에 특보 더미와 시차항 | 특보 계수의 95% 구간이 0을 포함하지 않는 품목군이 존재 |
| H3 | 반응에는 시차가 있는가 | 쇼핑 클릭(T1·T3)은 D+0~D+2에, 검색어(T4)는 그보다 먼저 정점을 찍는다 | 분포시차 모형(DLM). 프리화이트닝한 교차상관은 보조로만 쓴다 | 시차별 계수 곡선과 정점 시차, 구간 제시 |
| H4 | 첫 충격이 반복 충격보다 큰가 | 시즌 첫 영하·첫 30℃ 돌파일의 반응이 이후 같은 조건보다 크다 | 이벤트 순번을 상호작용항으로 둔 이벤트 스터디 | 첫 이벤트 계수 > 이후 계수, 차이 구간 제시 |
| H5 | 검색 지수는 실제 거래와 같이 움직이는가 | 월 집계한 의류 지수는 KOSIS 의복 온라인 거래액과 양의 상관을 보인다 | 월 단위 상관과 차분 상관 | 차분 상관이 양수이고 유의. 아니면 리포트의 해석 범위를 줄인다 |

다중 비교가 많다. 품목 × 시차 × 이벤트 조합에서 나온 p값은 **Benjamini–Hochberg로 보정**하고, 보정 전후를 같이 보고한다.

### 5.2 네이버 데이터랩 — NAVER API HUB

데이터랩은 2026-06 출시된 **NAVER API HUB**(네이버클라우드)로 옮겨졌다. 개발자센터는 2026-07-31부터 신규 신청을 받지 않으므로 **HUB 키만 발급한다.**

| 항목 | 값 |
|---|---|
| 호스트 | `https://naverapihub.apigw.ntruss.com` |
| 경로 | 쇼핑인사이트 `/shopping/v1/categories`, `/shopping/v1/category/{device,gender,age,keywords}`, `/shopping/v1/category/keyword/{device,gender,age}` · 검색어트렌드 `/search-trend/v1/search` |

| 한도 | 쇼핑인사이트·검색어트렌드 각 월 50,000건, 키당 50 RPS |
| 요금 | 한시적 무료. 유료 전환 시 사전 공지 |
| 데이터 보유 | 쇼핑인사이트 2017-08-01~, 검색어트렌드 2016-01-01~ |

설계에 주는 영향:

- **한도는 더 이상 제약이 아니다.** 전체 백필이 데이터랩 25회 안팎이다. 키워드를 수백 개로 늘리거나 T2 분해를 넓게 돌려도 된다. 대신 늘린 만큼 앵커 설계를 다시 검증해야 한다.
- **진짜 제약은 상대지수다.** `ratio`는 요청 묶음과 기간 안의 최댓값을 100으로 둔 값이라 배치마다 스케일이 다르다. 배치를 하나의 축에 올리는 방법은 §8.2에 정한다. 기간은 쪼개지 않는다. 자세한 내용은 `datasets.md` §2 T1.
- **일 배치에도 영향이 있다.** 요청 기간이 바뀌면 그 기간의 최댓값이 바뀌어 `ratio` 전체의 스케일이 달라진다. 운영 갱신은 전체 기간을 다시 받아 스냅샷으로 저장하고, 이전 스냅샷과 겹치는 구간의 배율을 기록하는 방식으로 설계한다 (§7.3).
- **유료 전환 위험**에 대비해 원천 응답은 모두 `data/raw/`에 보존하고, 재수집 없이 다시 계산할 수 있게 한다.

### 5.4 데이터 결정 사항

- 날씨 기준 지점은 서울 ASOS 108, 예보 구역은 기온 `11B10101`·육상 `11B00000`이다. 특보는 서울 하위 4개 권역 중 하나라도 발효되면 발효로 본다.
- T3는 클릭이 적은 날의 행을 아예 빼고 준다. 날짜축으로 reindex한 뒤 **0으로 채울지, 결측으로 둘지 품목별로 결정하고 근거를 남긴다.**
- T3의 `rescaled`는 카테고리마다 앵커가 달라 카테고리를 넘어 비교할 수 없다. 카테고리 간 비교는 T4를 쓴다.
- 쇼핑인사이트 클릭지수 전체가 2023 ~ 2026년에 약 1/6로 **구조적으로 하락**했다(EDA §2.3). 연도를 넘는 비교에는 카테고리 점유율로 바꾸거나 T4로 교차 확인한다.
- T3에서 희소한 키워드 7개는 조회 cid가 실제 카테고리와 맞지 않아서 생겼다(EDA §2.2). cid를 고치거나 T4로 대체한다.
- 중기예보 최소 리드타임이 **2024-12-02부터 3일 → 4일로 바뀌었다**(EDA §1.1). 예보 피처에는 기간 구분을 붙인다.
- `configs/categories.yaml`의 키워드 목록과 trigger는 가설이다. 백필과 EDA 뒤에 고치고, 바꾼 이유를 커밋 메시지와 리포트에 남긴다.

## 7. 시스템 설계

### 7.1 데이터 흐름

```
수집(collect)          정제(transform)              피처(features)          모델(model)            서빙(serve)
───────────────        ─────────────────           ──────────────          ─────────────          ──────────────
KMA API Hub   ─┐       weather_daily               feature_table           backtest 결과           artifacts/*.json
NAVER API HUB ─┼─▶ raw ─▶ weather_forecast_daily ─▶ (target_date ×    ─▶   학습된 모델       ─▶   (예측·분석 결과)
공공데이터    ─┘  (CSV)  shopping_trend_daily         item, as-of)          model card                   │
                         derived_event                                                                   ▼
                         (검증된 테이블)                                                            웹 서비스
```

- **raw**: API 응답을 최소 가공만 해서 CSV로 둔다. 정규화·조인을 하지 않는다. 규칙이 바뀌어도 API를 다시 부르지 않기 위해서다.
- **processed**: 스키마가 고정된 테이블. `datasets.md` §7의 스키마를 따른다. 형식은 Parquet를 권장한다.
- **features**: `(target_date, item, as_of)` 단위. `as_of`는 이 행의 피처가 계산된 시점이다. 누수 검사가 이 컬럼에 기댄다.
- **artifacts**: 웹 서비스가 읽는 정적 JSON. 서비스는 모델이나 원천 데이터에 직접 접근하지 않는다.

### 7.2 엔지니어링 원칙

- 각 단계는 CLI로 실행하고 **멱등**이어야 한다. 같은 입력이면 같은 출력이 나온다.
- 단계 사이의 테이블은 **스키마 검증**을 거친다. 도구(pandera 등)는 자유지만 컬럼 타입, 키 유일성, 값 범위, 날짜 연속성을 검사한다.
- 비밀값은 `.env` 또는 `configs/secrets.yaml`에만 둔다. 둘 다 `.gitignore` 대상이다.
- 수집기는 API 응답 이상을 조용히 넘기지 않는다. 행 수 0, 앵커 결측, 예상 밖 컬럼은 오류로 올린다.

### 7.3 일 배치 (확장 범위)

일 배치를 만든다면 다음 순서를 지킨다.

1. 기상 원천은 증분 수집한다 (어제 관측, 오늘 발표분).
2. 데이터랩은 **전체 기간을 다시 받아** 날짜가 붙은 스냅샷으로 저장한다. 이전 스냅샷과 겹치는 구간에서 같은 품목의 `ratio` 배율을 기록해 스케일 이동을 감시한다. 배율이 품목마다 다르면 원천 쪽 변화를 의심한다.
3. 피처 → 예측 → artifacts 갱신. 실패하면 이전 artifacts를 유지하고 서비스에 "데이터 기준일"을 표시한다.

스케줄러는 cron, GitHub Actions schedule 중 하나를 고른다. 선택 이유는 ADR로 남긴다.

## 8. Track A·B — 분석과 예측

### 8.1 예측 문제 정의

| 항목 | 정의 |
|---|---|
| 예측 시점 | 매일 18시 KST 중기예보 발표 직후 |
| 대상 | 대상일 D의 품목별 수요. 기본 D = 발표일 + 최소 리드타임(2024-12-02 이후 4일, 그 전 3일). 학습 구간이 두 기간에 걸치므로 리드타임 구간을 피처로 넣는다 |
| 입력 | 발표 시점에 공개돼 있던 데이터: 그 발표분의 예보(최저·최고기온, 강수확률, 하늘 상태), **발표 전일까지**의 관측과 수요 지수, 캘린더 |
| 출력 | ① 품목별 lift 예측값과 예측 구간 ② lift가 클 품목 Top-K (K=3, 5) |
| 품목 단위 | T3 키워드 30개를 기본으로 한다. T1 중분류는 보조 |

D+1 예측은 단기예보 과거 발표분을 확보할 수 있을 때만 범위에 넣는다(§13 Q1). 확보하지 못하면 "관측 기온을 넣은 D+1 모형"은 **실전에서 쓸 수 없는 상한선 참고치**로만 보고한다.

### 8.2 목표 변수

원 지수는 계절 패턴이 대부분이라 그대로 맞히면 달력을 맞히는 것과 다르지 않다. 목표는 계절성을 걷어낸 **lift**로 정의한다. 그 전에 배치마다 다른 스케일부터 맞춘다.

**① 배치 스케일 맞추기 — 날짜별 `rescaled`를 쓰지 않는다**

수집기가 저장하는 `rescaled = ratio / 같은 날 앵커 ratio`는 같은 날 품목끼리 비교할 때만 쓴다. 시계열 목표로 쓰면 **앵커 자신의 계절성이 모든 품목에 거꾸로 섞인다.** 2023-01 ~ 2026-07 백필(`data/raw/datalab_*/all_years.csv`)에서 T3·T4 앵커 `반팔티`의 월 중앙값은 1월 1.4, 5월 9.3으로 6배 넘게 움직였다. 배치 간 배율은 날짜와 무관한 상수로 확인됐다(EDA §2.1). 이대로면 여름에 모든 품목의 수요가 떨어진 것처럼 보이고, H1~H4는 품목이 아니라 반팔티를 측정하게 된다.

모든 배치가 같은 기간을 요청하므로 앵커 시계열의 모양은 배치마다 같고 크기만 다르다. 그래서 **배치마다 상수 하나**로 맞춘다.

```
c(batch)     = median_D( anchor_ratio(기준 배치, D) / anchor_ratio(batch, D) )   # 배치당 상수 1개
level(i, D)  = ratio(i, D) × c(batch(i))
```

- 기준 배치는 아무 배치나 하나 고정한다. 앵커 `ratio`가 0인 날은 중앙값 계산에서 뺀다.
- 배치 안의 앵커 비율이 날짜마다 크게 흔들리면(예: 반올림 때문에 작은 값끼리 나눈 경우) 그 배치를 표시하고 원인을 본다.
- T3는 카테고리마다 앵커가 달라 cid를 넘어 `level`을 비교할 수 없다. 이 제약은 그대로 남는다.
- 원천에 `ratio`, `batch_id`, `is_anchor`가 이미 저장돼 있으므로 수집기를 고치지 않고 transform 단계에서 계산한다. 단위 테스트를 둔다.

**② lift**

```
y(i, D)    = log(level(i, D) + ε) − baseline(i, D)
baseline   = 그 품목의 계절·요일·공휴일 성분 (STL/MSTL 또는 회귀로 추정)
```

- `ε`과 0 처리 규칙은 §5.4 결정을 따른다.
- baseline은 **각 폴드의 학습 구간 데이터로만 적합**한다. 전체 기간으로 적합하면 미래 정보가 섞인다.
- 정의를 바꾸면 백테스트를 전부 다시 돌린다.

### 8.3 분석 방법 (Track A)

- 계절 분해: 품목별 STL 또는 MSTL(주·연 주기). 분해 잔차가 백색잡음에 가까운지 확인한다.
- 이벤트 정의: `derived_event`에 규칙 기반 이벤트를 만든다. 첫 영하, 일교차 10℃ 이상, 전일 대비 ±7℃, 특보 발효·해제, 장마 시작·종료. 임계값은 설정 파일로 빼서 바꿔 볼 수 있게 한다.
- 이벤트 스터디: 이벤트일 기준 −7 ~ +7일 lift 경로와 구간. 이벤트가 겹치는 날은 따로 표시하거나 제외한다.
- 분포시차 모형: 기온·변화량·특보의 0~7일 시차 효과. 계수 곡선을 그림으로 낸다.
- 강건성: 코로나 구간 포함 여부, 임계값 ±1단계, 0 채움 규칙 변경, T3 대신 T4 사용. 결론이 뒤집히는 조건을 표로 정리한다.

### 8.4 누수 방지 규칙

1. 대상일 D의 피처에 **D 또는 그 이후의 관측을 쓰지 않는다.** 날씨 입력은 발표 시점의 예보만 쓴다.
2. 18시 발표 시점에는 그날의 일 관측과 클릭 지수가 아직 없다. 관측과 수요 지수의 지연값은 **발표 전일까지만** 쓴다. 7일 이동평균도 발표 전일에서 끝나야 한다.
3. 정규화 통계(평균·표준편차·baseline)는 각 백테스트 폴드의 학습 구간에서만 계산한다.
4. 데이터랩 `ratio`는 요청 기간 전체의 최댓값으로 스케일이 정해진다. 미래 구간이 들어간 요청이라 스케일에 미래 정보가 약간 섞이지만, 목표가 log 차이(lift)라 상수 배율은 상쇄된다. 이 한계를 모델 카드에 적는다.
5. 위 규칙을 **테스트 코드로** 검사한다. 피처마다 "공개 시각"을 정의하고, 피처 테이블의 모든 행에서 각 피처의 공개 시각이 예측 시각(발표 시각)보다 앞서는지 확인한다. `as_of < target_date` 정도의 검사로는 발표일 당일 관측이 섞이는 경우를 잡지 못한다.

### 8.5 평가

**검증 방식**: 롤링 오리진 백테스트. 학습 구간을 늘려 가며 다음 1개월을 예측한다. 학습은 2018-01부터 쓰고(코로나 구간은 더미 또는 가중치로 처리, 처리 방식은 ADR), 평가 폴드는 2023-01부터 홀드아웃 직전까지의 월이다. 마지막 12개월 홀드아웃은 최종 모델 한 번에만 쓴다. 기본 분석 구간(2023~)만으로 학습하면 첫 폴드의 학습 기간이 1년이 안 돼 계절 baseline을 추정할 수 없다.

**베이스라인** (반드시 모두 구현):

| 이름 | 정의 |
|---|---|
| B0 계절 나이브 | 작년 같은 주 같은 요일의 lift |
| B1 지속 | 발표 전일의 lift를 그대로 |
| B2 기후값 | 대상일 기온 평년값만 넣은 선형 모형 |
| B3 예보 선형 | 예보 피처만 넣은 정규화 선형 모형 |

**후보 모델**: 품목 전체를 하나로 학습하는 글로벌 GBDT(LightGBM 등)를 기본으로 하고, 품목 ID를 범주형 피처로 쓴다. 다른 구조(계층 모형, 시계열 딥러닝 등)를 시도해도 되지만 베이스라인과 같은 백테스트를 통과해야 한다.

**지표와 합격선**:

| 구분 | 지표 | 합격선 |
|---|---|---|
| 점 예측 | MAE(lift), B0 대비 스킬 = 1 − MAE/MAE_B0 | 품목 평균 스킬 ≥ 0.10, 과반 품목에서 양수 |
| 순위 | NDCG@3, Precision@3 (실제 lift Top-3 대비) | B0 대비 개선, 폴드별 개선 부호 검정 p < 0.05 |
| 이벤트 구간 | 이벤트 ±3일 MAE | B0 대비 개선이 평시보다 크다 (모델이 날씨를 실제로 쓰고 있다는 근거) |
| 구간 예측 (확장) | 80% 구간 실제 포함률 | 0.75 ~ 0.85 |

합격선을 못 넘어도 실패로 끝내지 않는다. 어느 품목·계절에서 날씨 신호가 있고 없는지를 보이는 것도 결과다. 다만 넘지 못한 사실은 숨기지 않고 리포트와 모델 카드에 적는다.

**모델 카드**에 적을 것: 학습 데이터 기간과 스냅샷, 피처 목록, 백테스트 결과표, 알려진 한계(상대지수, 서울×전국, 예보 리드타임), 재학습 방법.

## 9. Track C — 웹 서비스

### 9.1 스택

미리 정하지 않는다. 2주차까지 고르고 ADR로 이유를 남긴다. 다음 조건만 지킨다.

- 서비스는 **사전 계산된 artifacts만 읽는다.** 요청 시점에 모델을 돌리거나 외부 API를 부르지 않는다.
- 프론트엔드에 비밀값이 들어가지 않는다.
- 무료 호스팅에 배포할 수 있어야 한다.

참고 조합: ① 정적 사이트(React·Svelte 등) + 정적 JSON ② FastAPI + SPA ③ Streamlit 등 파이썬 대시보드. ③은 빠르지만 §9.3의 품질 기준을 맞추기 어렵다.

### 9.2 화면 요구사항

| 화면 | 내용 | 수용 기준 |
|---|---|---|
| 예보 보드 | 예측 대상일(D+4)의 예보 요약과 품목 Top-5 lift, 예측 구간 | 데이터 기준일·모델 버전 표시. 품목 클릭 시 상세로 이동 |

| CI | GitHub Actions: lint → test → (웹) build. PR마다 실행 |
| 노트북 | 탐색용으로만 쓴다. 리포트에 들어가는 그림은 `src/`의 함수로 다시 만든다. 출력이 큰 노트북은 커밋 전에 출력을 지운다 |
| 데이터 커밋 | raw 기상 데이터는 커밋하지 않는다(재수집 가능). 데이터랩 원천 스냅샷은 커밋하거나 릴리스 자산으로 보관한다(유료 전환 대비) |
| 커밋·PR | 커밋 하나에 의도 하나. PR 본문에 `배경`, `변경 내용`, `검증`을 쓴다. 작성자 정보(`git config user.name/email`)를 설정한다 |
| 결정 기록 | `docs/adr/NNNN-제목.md`. 스택 선택, 목표 정의, 0 채움 규칙처럼 결과를 바꾸는 결정 |

현재 저장소에는 `tests/test_datalab.py`가 있다. 수집기의 같은 날 재정규화와 배치 구성, HUB 오류 파싱을 검사한다. 이 수준을 다른 모듈에도 맞춘다.
